# Methodology

How the NZ-OCDS Mapping was built.

## Inputs

The mapping is built by cross-referencing five published sources:

1. **OCDS 1.1.5 release schema** (1,321 fields across 9 sections) — [open-contracting.org/data-standard](https://www.open-contracting.org/data-standard/)
2. **OCDS 1.2-dev codelists** (31 controlled vocabularies) — [`open-contracting/standard` GitHub repo](https://github.com/open-contracting/standard/tree/1.2-dev/schema/codelists)
3. **MBIE-published GETS schema** (32 fields across 4 tables: Tender, Supplier, Region, UNSPSC) — [mbie.govt.nz/open-data](https://www.mbie.govt.nz/cross-government-functions/new-zealand-government-procurement-and-property/open-data)
4. **NZ Government Procurement Rules** 5th edition (August 2025): 47 Rules + 2 Appendices + Glossary
5. **NZGP Approved Government Model Templates (A-GMTs)** — [procurement.govt.nz/templates](https://www.procurement.govt.nz/templates/)

Plus comparative references:
- NSW Treasury OCDS publication on the [OCP Data Registry](https://data.open-contracting.org/en/publication/11) (cautionary tale: discontinued, undocumented additional fields)
- NSW Government Open Data Publishing Guidelines V3.0 (Nov 2022) — adapted for the Publishing Governance sheet
- NSW Information Classification Labelling and Handling Guidelines V2.3 (2021) — adapted for the Sensitivity Classification sheet

## Process

For every OCDS path of meaningful procurement-publication interest, the mapping classifies it as one of:

| Status | Meaning |
|---|---|
| **Direct** | Value flows straight from a GETS field as-is |
| **Derived** | Computed from one or more GETS fields |
| **Vocab Translation** | GETS value translated via a controlled-list mapping |
| **Constant** | Hardcoded (e.g. currency = NZD) |
| **NZ Extension** | Proposed NZ-specific extension; data exists per Rules but no native OCDS field |
| **Template-sourced** | Captured in NZGP Approved Government Model Templates but not currently published |
| **Rule-mandated** | Mandated by a specific Rule to exist but no current structured source |
| **Gap** | Not collected by GETS, Rules, or templates |

## The core finding

Of 114 paths analysed in v0.4:

- **~32%** flow from GETS today (Direct + Derived)
- **~17%** are mandated to exist by Rules but not published structurally
- **~12%** are captured in mandatory NZGP templates but not centrally published
- **~27%** are NZ-specific extensions, each anchored to a Rule + glossary entry
- The remainder split between constants (7%), vocab translations (3%), and genuine gaps (3%)

So **~80% of the OCDS-NZ gap closes by structuring data the Rules already require to exist.**

## NZ extensions — anchoring approach

Every proposed NZ extension is anchored to:

1. **A specific Procurement Rule** that mandates the data to exist (or makes it relevant). This grounds the extension in published government policy, not vendor preference.
2. **A glossary entry** from the Rules' formal terminology, where applicable.

Example: `nz-economic-benefits` extension cites:
- **Rule 8** mandates ≥10% evaluation weighting for economic benefits
- **Rule 8(4)** enumerates 7 benefit categories
- **Rule 8(5)(d)** requires contract provisions to deliver agreed benefits
- **Glossary "New Zealand business"** clarifies that for Rule 8 purposes the term includes Australian business (Trans-Tasman scope)

This anchoring strategy serves two purposes:

- **Defensibility**: when OCP / MBIE / NZGP review the proposal, every field traces to a public, official document
- **Filling the policy vacuum**: NZ0029's IRM midterm review explicitly notes that "specification of new mandatory fields for disclosure have yet to be determined" — the Rules-anchored extensions are a substantive proposal for what those fields should be

## Honest gaps

OCDS sections largely unrecoverable from current GETS data:

- **Planning** — partially mandated by Rule 6 (12 elements) + Rule 7 (estimated value) + Rule 37 (Future Procurement Opportunities) to exist in agency procurement plans, but not publicly published in structured form
- **Contract performance / implementation** — mandated by Rules 34 (9 mandatory CMS fields) and 35 (KPIs) to exist in agency contract management systems, but not centralised
- **Bids** — Rule 5 protects bid content as commercial-in-confidence; only bid statistics could be published, and these are not currently collected centrally

These are **publication gaps, not data gaps**. The data is mandated by law to exist; it isn't structured for public output.

OCDS allows partial publication. The honest declaration of these gaps in the mapping is itself a feature — it gives downstream consumers a clear picture of what the feed will and won't include.

## Build process

The spreadsheet is generated by a Python script (`mapping/build_ocds_mapping.py`) rather than authored by hand. Reasons:

- **Version-controllable**: Python source is plain text; git diffs show every changed row.
- **Reproducible**: anyone with the script can regenerate the exact file.
- **Auditable**: every cell traces to a line of code with a comment.
- **Diff-friendly review**: PR reviewers can comment on specific lines.
- **Programmatic consistency**: status colour-coding, codelist URLs, fonts applied uniformly.
- **Mirrors Foundry's Pipeline Builder pattern**: declare transforms once, regenerate output deterministically.

To regenerate:
```bash
cd mapping/
pip install openpyxl
python3 build_ocds_mapping.py
```

The `.xlsx` is the consumable artefact for non-coder reviewers (OCP Helpdesk, Transparency NZ). The script is the source of truth for changes.

## Versioning

- v0.x = pre-public research milestones. Each version is a substantive structural addition.
- v1.0 = first version submitted to OCP Helpdesk for formal review.
- v2.0 = first public release post-feed launch.

Each version is git-tagged so historical states are preserved even though only the latest `.xlsx` is checked in.
